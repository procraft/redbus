# Consume stream — контекст модуля

`internal/pkg/stream` владеет протоколом обмена по двунаправленному `Consume`: отправкой батча
клиенту и приёмом результата его обработки. Это единственное место, где сопоставляются запрос и
ответ, поэтому все инварианты фазы «батч ↔ ответ» живут здесь.

## Кто пишет в стрим

В один consume-стрим пишут два независимых источника:

- `grpcapi.Consume` — цикл чтения kafka (`databus.consumeLoop`);
- `repeater.repeatProcessor` — повторная отправка ранее неуспешных сообщений.

Они сериализуются `c.Lock()` внутри `ProcessMessageList`. Из-за второго источника счётчик
`batchSeq` общий на процесс, а не на `Stream`: объект `Stream` repeater создаёт заново на каждое
сообщение.

## Корреляция батча и результата

Сервер кладёт в `ConsumeResponse.batchId` идентификатор батча, клиент возвращает его в
`ConsumeRequest.batchId`. Правила приёма:

- `batchId == ""` — клиент собран до появления поля (Go SDK и Scala SDK ≤ 0.2.5). Для него
  сохраняется позиционное сопоставление: ответ считается ответом на текущий батч.
- `batchId == отправленному` — нормальный случай.
- любой другой `batchId` — поздний или чужой ответ. Он отбрасывается с логом, ожидание
  продолжается. Ронять из-за него consumer нельзя: именно так протокол терял фазу навсегда.

Поле добавлено additive-only (новые номера, `proto3` не отличает пустую строку от отсутствия), так
что развёрнутые клиенты продолжают работать с обновлённой шиной без изменений.

## Дедлайн ожидания результата

`ProcessMessageList` не ждёт `Recv` бесконечно. Бюджет считает `model.ConsumeLimits`:
`PerMessage * размер батча + Slack`, не больше `Max`. `PerMessage` берётся из
`ConsumeRequest.Connect.consumeTimeoutSec`, если клиент его объявил, иначе из
`config.grpc.consumeResultTimeout`. Сервер обязан быть терпеливее клиента, поэтому `Slack` (30 с)
заведомо больше клиентского запаса (5 с в Scala SDK): клиент должен успеть отработать свой таймаут
и переподключиться сам.

Просроченный батч закрывает стрим через `AbortFn`. Отмена контекста хендлера **не** будит
заблокированный `server.Recv()` — его будит только завершение RPC, то есть возврат из
gRPC-хендлера. Поэтому `AbortFn` делает две вещи: запоминает причину, чтобы
`grpcapi.Consume` вернул её статусом (клиент получит `onError`), и отменяет контекст, чтобы
хендлер вернулся. Второй `Recv` в отдельной горутине запускать нельзя — gRPC этого не допускает.

## Прочие инварианты

- `Recv` на закрытом клиентом стриме возвращает `(false, nil, nil)`; `ProcessMessageList`
  отдаёт в этом случае `(nil, nil)`. Оба вызывающих обязаны проверять `data == nil` до обращения
  к `data.ResultList`.
- Ошибки обёрнуты `model.ErrStream`; `grpcapi` превращает их в `model.ErrHandler`, а
  `databus.consumeLoop` по `model.ErrHandler` завершает чтение и закрывает стрим. Сравнивать
  ошибку с локальной копией `errors.New("error in handler")` нельзя: значения не совпадут, и
  ветка станет мёртвой.
